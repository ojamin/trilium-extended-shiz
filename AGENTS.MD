## Habit Dashboard notes

- The dashboard script lives in `habits/habit-dashboard.js` and now powers day, last-7, last-14, week (Monday anchor), two-week, and month views with inline entry editing, range summaries, groups, and rich metadata fields (slug override, reminders, streak goals/windows, colors, icons).
- When extending it, reuse the normalization helpers (`normalizeString`, `normalizeNumber`) to keep backend payloads safe, and keep modal action buttons inside their forms so submit events fire.
- All multi-day views render through the full-width summary stack (`renderRangeSummaryCards`) with the range header, compact two-line habit cards, and clickable day chips—there is no parallel table anymore, so keep metrics/UI tweaks focused there. Cards now show the icon/name + completion summary + badges/actions on line 1, with the day chips on line 2; maintain that two-line structure when extending.
- Styling now leans on Trilium theme tokens (`--detail-*`, `--shade-*`) and narrows spacing, with compact mode applying further reductions; the root `.habit-dashboard` maps those tokens through local `--hd-*` variables so reuse them if you need new surfaces and the colours stay aligned with the active theme.
- Theme fallbacks were reworked to rely on Trilium's pane/background tokens; avoid reintroducing hard-coded dark colours so light/dark theme switching stays accurate. Wide layouts include a progress ring to the left of each card—keep the `.habit-dashboard__progress-circle` markup/styles intact if you restyle it.
- Theme polish (`habit-dashboard/v12`): badges, chips, overlays, and modal shadows now pull from shared `--hd-*` tokens (using `color-mix`), and summary cards/progress rings tighten spacing below 900 px and collapse elegantly under 600 px. When extending styles, prefer those tokens so light/dark themes and responsive tweaks stay consistent.
- Habits/Entries books are created directly beneath the dashboard note (context) now, so each dashboard keeps its own data tree even when sharing the script note—be mindful when migrating existing setups.
- If you introduce new ranges or aggregation metrics, update `buildDateRange`, `normalizeDateForView`, `shiftDate`, and the summary-card builder together so navigation, backend collection, and visuals stay aligned.
- Color inputs now use the shared `buildColorField` helper to keep the text hex and `<input type="color">` in sync; reuse it whenever you surface another colour selector so UI + payload parsing stay aligned.
- Habits can be dragged within their group (table rows and summary cards) to persist new orders, and short-click/long-press interactions are wired through `performHabitQuickAction` + long-press handlers (short click = toggle/step forward, long press = open the entry editor). Extend those helpers for any new quick-action affordances.
- Quick actions support per-habit “Quick increment” metadata (set in the habit editor) and announce the result via the toast helper; make sure to update both the meta payload and `getHabitQuickStep` when introducing new habit types so the feedback stays consistent.
- Reordering is available via drag-and-drop and via keyboard/toolbar controls (Alt+↑/↓ on a habit row/card or the inline move buttons). Stick to `moveHabitByOffset`/`persistHabitOrder` so the badges, toasts, and status line stay in sync.
- The colour field swatches (and “Reset to theme” option) are wired through `buildColorField`; if you add more preset palettes, extend the swatch array in that helper and the matching CSS tokens.
- Multi-day views highlight the quick-action target day and today (date-chip classes `is-current-day` / `is-today`), and the new “This Week” header button calls `setView('week', { anchorDate })` to re-anchor navigation—keep that API in mind for future range shortcuts.
- Rolling streak calculations for all habit types (`habit-dashboard/v12`) follow this flow:
  1. Build a 365-day status timeline (success = at least one completed or skipped entry; missing days are failures) alongside a 60-day pre-roll for consecutive seeding.
  2. Pick the evaluation day: use today when it already has a completion or skip; otherwise evaluate yesterday (even if yesterday was a miss).
  3. Declare the streak “active” when the rolling `streakWindow` (per habit, default 7) ending on the evaluation day contains at least `streakGoal` successes. For shorter histories we fall back to total successes so a new habit can activate once the goal is reached.
  4. Walk backward until you encounter the first full window that fails the goal; the streak starts the day after that failure. The streak length equals the count of successful/skipped days between the start and evaluation day (failures inside the span don’t add to the total but are allowed so long as every window meets the goal).
  5. `longestStreak` applies the same rule to every possible end day in the 365-day lookback, keeping the segment with the most successful/skipped days (ties break on wider calendar span).
- Streak logic now runs for every habit type through the same rolling evaluator: a day is successful when it’s skipped or meets the configured target (check = true/false, numeric + time + value = value ≥ target, rating uses target if set). If no target exists we treat any recorded value as success, so legacy numeric/rating entries still contribute to streaks.
- Multi-day cards temporarily surface a copy-friendly “Streak debug” line (last ~30-day pattern, evaluation index/date, recent window counts) to help validate the algorithm while we iterate.
- Multi-day cards only surface the “Streak debug” line when either the dashboard note or the script note carries the `habitDebug` label (any value); omit the label in production so the extra diagnostics stay hidden.
- Celebrations & encouragements run through `buildCelebrationPayload`/`triggerCelebration`, which fire confetti overlays, card/row flashes, and motivational status lines when targets/streaks hit; reuse those helpers instead of rolling bespoke effects so the UX stays cohesive.
- Habits can opt into multiple entries per day (toggle in the habit editor). When enabled, entries are stored with unique keys (`habitId:YYYY-MM-DD:random`), day rows render a history list with edit/delete buttons, and range chips/summary logic operates on arrays of entries—use `getEntryForDate`/`summarizeEntriesForDay` helpers so you don’t have to juggle the raw arrays yourself.
- Long-press/quick-press logic now carries a `date` context: chips or rows trigger `performHabitQuickAction(habitId, date)` for a quick edit of the latest entry, while long-press (or modifier-click) opens `openEntryEditor` preloaded with the most recent entry—only attach `data-habit-trigger="primary"` to elements that should participate in this flow.
- Modifier-aware quick actions: short-presses with Ctrl/⌘/Alt/Shift now bypass the quick-action handler so the chip click falls through to the editor modal. When tweaking press logic, keep the `hasModifier` guard in `handleHabitPressStart/End` intact so power users can open editors without altering data.
- Streak lookbacks now lean on `CONSTANTS.streakPreseedDays` (consecutive seeding) plus `CONSTANTS.streakLookbackDays` (rolling window history). Adjust both knobs if performance or UX expectations change.
- Please auto-append future context or breaking changes here so any agent picks up the latest working knowledge; this note should keep growing as features land.
- Backend safety net: `Backend.resolveRootNoteId` now retains the last known dashboard note when context detection fails and the backend throws an explicit "Habit dashboard root note unavailable" error if it still can’t resolve. Reuse `Backend.call` rather than direct `runOnBackend` calls so this caching stays effective, and check the new `[habit-dashboard][backend] …` log lines for script/root-note fallbacks when debugging. The frontend bootstrap now only runs when `window` exists, so backend loads (for `runOnBackend`) won’t crash trying to read `api.startNote.noteId`.
- Logging now prefixes every line with the script version (current `habit-dashboard/v12`); bump `CONSTANTS.version` whenever behaviour changes so we can confirm deployed code from the console.
- Entry deletion from the modal/quick controls now routes through `deleteEntryKeys`, which issues a lightweight backend removal via entry labels—avoid calling the old `backend.deleteEntries` directly unless you need the original behaviour.

## Task Dashboard notes

- Core assets now live under `task-system/`: frontend UX in `scripts/task-dashboard-frontend.js`, shared helpers in `scripts/task-utils.js`, backend wiring in `scripts/task-service-backend.js`, and styles in `styles/task-dashboard.css` (`task-modal*` / `task-token-*` cover modal + token UI).
- Dashboard depth now defaults to 10 levels. The Filters panel exposes a “Depth (levels)” control that persists to the dashboard note (`taskDepth`), clamps between 1 and 25, and feeds straight into `collectTasks` so deeper hierarchies render without manual patches.
- Quick Add launches in a modal overlay. Single-task mode mirrors the original inputs; the Multiple tab accepts one task per line with optional `Title: description`, applying the shared status/due date/tag/role selections to every task in the batch.
- Tags and roles share the `buildTokenInput` chip control for Quick Add and the task detail drawer. It surfaces suggestions from `availableTags`/`availableRoles`, blocks duplicates, and lets authors add free-form entries—reuse it whenever you add new multi-select metadata.
- Search, the filter toggle, Quick Add, and Refresh now sit in the compact top action bar (`task-header-controls`); the title row holds the dashboard selector, view switch, and summary metrics on the right. Keep future controls in those lanes for predictable responsive wrapping.
- Search input is debounced (~220 ms) and keeps focus after dataset refreshes. When extending search behaviour, reuse `this.searchDebounce` so we don’t regress into the old focus-loss/redraw loop.
- Multi Quick Add calls `callService('createTask')` sequentially and triggers a single `refresh()` at the end; avoid looping `this.createTask` inside bulk flows because that method performs a full refresh per call by design.
- Modal and token styles are centralised—stick to the existing `task-modal-form`, `task-modal-actions`, and token classes if you extend the UI so light/dark theming, blur, and spacing stay consistent.
- Tasks now record status transitions in `taskStatusLog` (JSON label) and `taskStatusChangedAt`; any workflow that changes `taskStatus` must continue to run through `moveTask` / `updateTask` / `updateTaskOrders` so the log stays consistent for future “recently changed” filters.
- Default filters hide archived work; backlog is now visible by default. Filters use `hideBacklog/hideArchived` toggles (persisted via `taskHideBacklog`/`taskHideArchived` labels), so keep those consistent whenever you persist dashboard configs.
- Dashboard selectors now arrive strictly in tree order (pre-order). `task-service-backend.loadDashboardNotes` returns `treePath` (array of branch positions) alongside `treeDepth`, so any future UI that needs hierarchical context can use that path without recomputing it.
- List view defaults to sorting by status only (in-progress → todo → blocked → backlog → done → archived). Column headers are interactive—click to toggle direction, Shift/Ctrl/⌘+click to layer additional sort keys (priority, location, title, etc.) as needed. Headers surface the sort rank badges and Kanban keeps its existing priority/`taskOrder` behaviour.
- Kanban view now has a toolbar with sort controls (priority, due date, last changed, title, manual) and a toggle to show/hide empty columns. When custom sorts are active we disable drag reordering to avoid fighting the sort, and we surface pills listing statuses hidden by filters vs. columns collapsed for being empty.
- Cards in Kanban gained richer metadata: a location line with icon, capped role/tag chips with `+N` overflow, and an extended tooltip summarising status, due date, last change, roles, and tags.
- List view supports multi-select: use the checkbox column (with optional Shift for range) to pick tasks, then use the bulk bar for status/priority/due/pin updates. The bar respects the current filters, shows how many visible tasks are selected, and exposes quick actions for clearing selection or due dates. Backend exposes `bulkUpdateTasks` for these coordinated edits, so reuse that action instead of issuing per-task updates.
- List rows and kanban cards carry `status-*` and `priority-*` classes for themed tinting—stick to those when adding new badges so the colour system remains predictable.
- “Archive Done” button calls `archiveCompleted` (backend action) using the active dashboard root + depth; if you add new completion states ensure they continue to map to status `done` so this sweep works.
- The list “Location” column pulls dashboard titles by matching `task.parentNoteIds` against each dashboard’s `rootNoteId`. Reuse `getTaskLocation` to keep multi-dashboard membership and future filtering aligned.
- Header quick filters now include due-range chips (All/Overdue/Today/Next 7 days/No due), a pinned-only toggle, and the top tags/roles by frequency for one-click filtering. Keep these in sync if you add new filter keys.
- The Filters panel adds a “Updated within” selector that relies on `taskStatusChangedAt`; when introducing new status-manipulating flows make sure they emit log entries via `appendStatusLog`.
- List rows and kanban cards display relative “last changed” pills, and the task detail drawer surfaces a full status timeline (`task.statusHistory`). Formatting helpers live in `formatRelativeTime`/`formatDateTime`.
- Detail view also lists linked dashboards as quick chips that switch context; honour this UX when changing how parent links are stored.
- Pinning runs through the lightweight `updatePinned` backend action. Use it (instead of `updateTask`) for future quick pin affordances to avoid clobbering labels.
- Overview view includes role distribution (`insights.byRole`), so extend `computeInsights` accordingly if you add more aggregates.
- Keyboard shortcuts are intentionally disabled at the Task Dashboard level to avoid conflicts; rely on the on-screen controls instead.
